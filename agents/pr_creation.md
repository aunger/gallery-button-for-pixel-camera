# PR creation

## A PR is not always required

Before creating a PR, confirm one is warranted.
An Author may legitimately decline to open a PR when addressing the issue needs no code change, when it cannot fix the issue, or when the issue is flawed or should not be acted upon.
In those cases, follow "Declining to open a PR" in `pr_participation.md` instead of creating a PR. The rest of this document applies only once you have decided a PR is the right artifact.

## One topic per PR

Do not combine unrelated work in a single PR. You may resolve multiple issues with one PR, but *only* if they're both symptoms of the same technical issue.

Each PR must originate from its own dedicated branch.
If your branch is not clean, fix it now by making a new branch and cherry-picking commits.

## The PR's Title

The title must name the PR's *solution*. Only name the issue's *problem* if you have space for both.

## The PR's Description

Include the #XYZ issue number of the issue that this PR addresses.
If the PR completes the issue, write "Fixes #XYZ". Explain how the changes fix the issue.

## Test plan checkboxes

Do not add a checkbox, or otherwise state a requirement, for something the automated test suite already covers.
Reserve checkboxes for steps automated CI does not perform, such as manual verification or changes outside the repo.

## No bylines

Do not append any attribution byline, session URL, or "Generated by Claude" footer to PR descriptions or comments.
No `---` divider followed by attribution text.
No `Co-authored-by: Claude` trailer in PR bodies.
